### On the planning-step model choice

The reasoning already recorded in `claude/models.py` is: planning is "outlining from a fixed set of sources," treated as structured extraction rather than original writing, so it's routed to Haiku alongside research and adaptation, while `generate` and `evaluate` (the two steps judged most quality-sensitive) get Sonnet.

Worth being honest about where that reasoning is solid and where it's more of an assumption than a proven fact:

- **Solid part:** the plan's job — pick section headings and assign source IDs to each — is close to extraction/structuring, and Haiku is priced roughly 2x cheaper on input and output than Sonnet. Every request pays for a plan call, so this is the highest-volume structured-output call in the pipeline; a cheaper model here compounds across every run in a way a one-off Sonnet call wouldn't.
- **The actual test of the reasoning: does a weak plan cause downstream damage that costs more than it saves?** Session 3's test #10 is a data point *against* a bad plan being the cause of its own revision cycles — the repeated "revise" verdicts there were about source-grounding thinness (one source stretched too far), not a structurally bad outline; the outline itself wasn't what evaluation kept flagging. That's mild evidence the current split is fine, not proof of it — a single test case isn't enough to conclude the plan step is never the bottleneck.
- **Where the assumption could break:** if a badly-organized outline ever forces multiple *generate* (Sonnet, the expensive step) revisions to fix — i.e. the cheap step's mistake gets paid for in the expensive step's retries — that would flip the tradeoff, since Sonnet revisions cost roughly 5x more per call than a single upgraded Haiku→Sonnet planning call would have. That hasn't been observed yet in testing, but it also hasn't been specifically tested for (no case so far had a genuinely bad outline as the evaluation's complaint).
- **Honest bottom line:** the model choice is a reasonable, cost-aware default backed by real per-token pricing math, not just "it was the default" — but it's calibrated on assumption plus one session of testing, not a controlled comparison against routing `plan` through Sonnet. If cost data ever shows a request burning multiple `generate` revisions where the evaluation feedback traces back to outline structure rather than source grounding, that's the signal to move `plan` to Sonnet for that step.

## Session 2 — 2026-09-16, `TEST_INTAKE_REQUESTS.md` #4 (all-sources-unusable case)

**Setup:** a request with two URL attachments, both resolving to placeholder/boilerplate content ("Example Domain" — functionally equivalent to EDGE_CASES.md #7, "scrape returns a page but no article text"). Raw idea: *"What the latest changes to X's API mean for social media schedulers."*

**Observed:**

1. **Both sources were correctly identified as unusable** — the `sources` list showed both as `discarded`, not `selected`. Good: the system didn't pretend garbage sources were real grounding material.
2. **The pipeline proceeded anyway** — research → planning → 3 full generate/evaluate cycles → revision cap reached → escalated to human review. This is EDGE_CASES.md **#6** ("all sources fail... and the pipeline proceeds anyway") actually occurring, not just a theoretical risk: the article was generated three separate times on zero usable source material.
3. **Cost:** 8 Claude calls, 18,600 input / 13,249 output tokens, **$0.1651** — directly visible for the first time via the new usage panel, which is exactly the kind of number this finding is about.
4. **UI bug found in the same session:** a stale red "failed to load request" banner was rendered *above* a fully-populated, up-to-date page. Root cause: `RequestDetailClient`'s polling `load()` set `error` on a failed fetch but never cleared it on a subsequent successful one — so a single transient blip (a 5-second poll racing a mid-update read, or a cold-start timeout) left a permanent false-failure banner on an otherwise-working page. **Fixed** — `load()` now clears `error` on every successful response, matching how each action handler already resets `error` before running.

**Question raised: should the system check sources before starting research, and break on none/404?**

Not quite — a hard pre-check would conflict with the PRD directly. **Testing Scenario 1 ("Raw Idea Request") requires the system to produce article options from an idea alone, with no source URL at all** — zero sources is a *supported, required* input shape, not a failure condition. Blocking on "no sources" would break that scenario. The PRD's actual requirement (Scenario 3) is narrower: *"show which sources informed the output and avoid claims not supported by the available material"* — it's about honest attribution and grounding, not about mandating sources exist.

So the real gap isn't "should we require sources" — it's that the system doesn't yet distinguish **"no sources were given" (fine, expected)** from **"sources were given but all turned out unusable" (should cost less and be flagged sooner)**. Two changes worth considering, not yet made:

- **Stop paying for revision attempts that can't fix the actual problem.** All three evaluate passes almost certainly failed for the same reason — a source-grounding floor score — because rewording the article can't manufacture source material that doesn't exist. A cheap, deterministic check (in the spirit of `claude/quality_guards.py`'s existing hard guards) could detect "this draft has zero `source_ids_used` and the evaluation's dominant failure is source grounding" and skip straight to human review after one attempt instead of spending the full revision cap. This is a direct, well-evidenced cost-awareness fix — the $0.1651 here was mostly two wasted generate+evaluate cycles that were never going to pass.
- **Surface it earlier and more clearly than a rubric score.** Right now a human only learns "there was no usable source material" by reading the evaluation feedback text after the fact. A `stage_events` note right after research completes — "0 of 2 attachments produced usable source content" — would make this visible at the point it happens, not three drafts later. This is squarely what EDGE_CASES.md #6 already calls for; this session is the confirmation that it actually happens in practice, not just a documented risk.

**Both implemented — 2026-09-16:**

- **Ungroundable-draft guard** (`claude/quality_guards.py::is_ungroundable`, wired into `worker/handlers/evaluate.py`): when a draft has zero `source_ids_used` and the evaluator's own `rubric_scores.source_grounding` is at or below 2/5, the loop now stops after that one attempt and sends the draft to human review immediately, with a `stage_events` entry explaining why ("revising the wording can't fix that"), instead of spending the rest of the revision cap. A low grounding score on a draft that *does* have real sources still revises normally — the guard is specifically about zero sources, not just a bad score. Covered by new tests in `test_quality_guards.py` and `test_evaluation_loop.py`.
- **Discard/failure reason on every source** (`sources.discard_reason`, migration `0005`): the source-selection prompt (`claude/prompts/research.py`) now requires a specific `unusable_reason` whenever it marks a source `usable=false` (e.g. "login/paywall wall", "JS-rendered shell with no article text" — not a generic "not useful"), and a URL that fails to scrape entirely now gets its own `sources` row with `status=failed` and the scrape error as the reason, instead of only being recorded in `stage_events` where a reviewer would never see it. Both show up directly under the source in the UI: *"Couldn't retrieve this source: ..."* for failed scrapes, *"Not used: ..."* for discarded ones.
